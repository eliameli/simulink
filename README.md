# GPS-free навигация: dead reckoning + привязка к карте (Simulink, v0)

Учебный проект: имитация инерциального датчика (акселерометр + гироскоп)
на движущемся по дорожной сети автомобиле, восстановление траектории по
показаниям датчика ("dead reckoning") и привязка восстановленной
траектории к известной карте дорог **без использования GPS**.

## Идея проекта (по заданию)

Проект состоит из двух независимых частей:

1. **Часть 1 — генератор эталона + карта + модель датчика.**
   Скрипты строят синтетическую дорожную сеть (карту), эталонную
   (истинную, точную) траекторию автомобиля по этой сети и подают на
   вход Simulink-модели "истинные" ускорение/угловую скорость. Внутри
   модели блок датчика превращает их в *измеренные* (зашумлённые)
   значения — с учётом типичных ошибок MEMS-датчиков: шум и смещение
   (bias), которое ещё и медленно "плывёт" во времени (bias random walk).
2. **Часть 2 — навигация без GPS.**
   По зашумлённым показаниям датчика Simulink-модель восстанавливает
   положение автомобиля методом счисления пути (dead reckoning),
   интегрируя не методом Эйлера, а методом Рунге-Кутты 4-го порядка
   (RK4). Восстановленная траектория неизбежно "уплывает" от истинной
   (типичная проблема чистого dead reckoning). Блок привязки к карте
   (map matching) "прижимает" оценённое положение к ближайшей дороге на
   карте, компенсируя часть накопленной ошибки — без GPS, только по
   карте и датчику.

Это **нулевая версия (v0)**: карта — синтетическая (не настоящий OSM),
привязка к карте — самая простая (проекция на ближайший отрезок дороги,
без учёта истории движения). Это сделано специально, чтобы сначала
проверить концепцию целиком на простом примере, а потом усложнять
отдельные части (см. раздел "Куда развивать дальше").

## Структура репозитория

```
map/
  generate_map.m          - строит синтетическую дорожную сеть (граф: nodes+edges)
truth/
  generate_trajectory.m   - строит эталонную (истинную) траекторию по карте
sim/
  unicycle_rk4_step.m     - RK4-шаг кинематической модели автомобиля (общая логика)
  map_match_nearest.m     - привязка точки к ближайшему отрезку дороги (справочная copy)
  sensor_params.m         - параметры модели ошибок акселерометра/гироскопа
  build_model.m           - программно строит Simulink-модель gps_free_nav_v0.slx
  run_v0.m                - главный скрипт: карта -> эталон -> модель -> симуляция -> графики
  blocks/
    ins_mechanization_block.m  - текст кода MATLAB Function блока "INS Mechanization (RK4)"
    map_matching_block.m       - текст кода MATLAB Function блока "Map Matching"
models/
  (сюда build_model.m сохранит gps_free_nav_v0.slx при первом запуске)
```

Модель `.slx` не лежит в репозитории в готовом виде — она **генерируется
локально** скриптом `build_model.m` (у меня нет MATLAB, чтобы собрать и
проверить бинарный `.slx` файл; зато .m-скрипты, которые её строят,
можно читать, проверять и версионировать в git как обычный текст).

## Как запустить

В MATLAB R2024a:

```matlab
cd sim
run_v0
```

Скрипт сам:
1. сгенерирует карту (`map/road_map.mat`);
2. сгенерирует эталонную траекторию (`truth/truth_trajectory.mat`);
3. соберёт `models/gps_free_nav_v0.slx`, если его ещё нет
   (если он уже есть — просто откроет);
4. запустит симуляцию;
5. построит графики: карта + истинная траектория + "поплывшая"
   dead-reckoning-траектория + траектория после привязки к карте, плюс
   график накопленной ошибки во времени.

### Если сборка модели даст сбой на каком-то блоке

`build_model.m` создаёт два блока MATLAB Function программно (через
Stateflow API) — это единственная "хрупкая" часть скрипта, которую я не
мог проверить без MATLAB. Если при сборке появится предупреждение по
конкретному блоку, откройте модель, дважды кликните на пустой блок и
вставьте код из соответствующего файла в `sim/blocks/` вручную — там
лежит ровно тот код, который скрипт пытается вставить автоматически.

## Что учитывается в модели ошибок датчика (v0)

Для акселерометра и гироскопа отдельно (см. `sim/sensor_params.m`):

- **bias0** — постоянное смещение "при включении" (turn-on bias);
- **bias random walk** — смещение медленно "плывёt" во времени
  (реализовано как белый шум, пропущенный через интегратор);
- **white noise** — обычный измерительный шум на каждом шаге.

Это упрощённая, но содержательная модель типичных ошибок MEMS-датчиков
(без имитации конкретного датчика по даташиту — цифры условные,
порядка типичных потребительских IMU).

## Куда развивать дальше (v1+)

- Заменить синтетическую карту на настоящие данные (OpenStreetMap /
  Automated Driving Toolbox `drivingScenario`, если появится лицензия).
- Заменить "наивную" привязку к ближайшему отрезку на привязку с учётом
  истории движения (например, Hidden Markov Model по графу дорог, либо
  частичный фильтр/Partical Filter) — устойчивее к шуму и развилкам.
- Сделать начальное положение/курс параметром модели, а не константой
  внутри блока (сейчас v0 жёстко предполагает старт в узле карты (0,0)
  с курсом на восток — см. комментарий в `sim/blocks/ins_mechanization_block.m`).
- Объединить dead reckoning и map matching через фильтр Калмана
  (коррекция оценки, а не жёсткое "прилипание" к дороге).
- Если появятся Navigation Toolbox / Sensor Fusion and Tracking Toolbox
  — заменить самодельный блок датчика на `imuSensor`, а мехенизацию — на
  `insfilterMARG`/`insfilterAsync`, сравнить с самодельной реализацией.
